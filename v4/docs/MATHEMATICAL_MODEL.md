# Математическая постановка v4

## Откуда взялся JSON
Предоставленный TXT содержит разнородный цифровой след: публикации, образование, ДПО/ПК, учёную степень и звание, дисциплины и нагрузку. `profile_example_from_trace.json` — **не результат автоматического парсинга TXT**. Это вручную структурированный демонстрационный объект, показывающий целевую схему. В промышленном сервисе ручной шаг заменяется ETL/ELT.

Цепочка: источник → извлечение → нормализация → дедупликация → привязка к онтологии → свидетельства компетенций → версия профиля.

Для каждой записи сохраняются `source_system`, `source_record_id`, `timestamp`, `raw_value`, `normalized_value`, `mapping_version`.

## Модель
Для сотрудника i, источника s и компетенции k:
`w_is = norm(x_is) · q_s · d_is`

`C_ik = Σ_s w_is · a_isk`

`p_ik = C_ik / max_k C_ik`

Профиль подразделения:
`P_Dk = 1 − Π_i(1 − p_ik)`

В базовой модели **нет административного веса сотрудника**: должность и статус не умножают компетенцию. Нагрузка и доступность учитываются только при формировании проектной команды.

Глубина:
`Depth_Dk = max_i p_ik`

Проект имеет требуемый профиль `g_t`:
`Coverage_Dk(t) = min(P_Dk / g_tk, 1)`

`Coverage(D,t) = Σ_k g_tk·Coverage_Dk(t) / Σ_k g_tk`

`Gap_Dk(t) = max(g_tk − P_Dk, 0)`

Косинусная мера:
`Fit(i,t) = (p_i·g_t)/(||p_i|| ||g_t||)` — вспомогательная мера «Релевантность проекту».

Для команды:
`P_Ak = 1 − Π_i∈A(1 − p_ik)`

Ограничение нагрузки:
`load_i + project_load_i ≤ capacity_i`.

## Где видны «белые пятна»
1. Матрица проекта: требуется / есть / дефицит / кто закрывает.
2. Карта подразделения: тематические кластеры, сильные зоны, дублирование и дефициты.
3. Рекомендации: внутренний кандидат/команда либо внешняя компетенция/партнёр.
4. История изменений: какие дефициты появились или исчезли после update.

## Онтология
КРМ задаёт эталонные описания компетенций. В демо включены MF-1…MF-4 и BD-1…BD-3 из новой презентации. УДК используется для областей знаний и классификации предметной области, но не заменяет словарь компетенций.

## Хранение и update
`raw → normalized → competency → analytics → presentation`.

Raw-слой хранится во внутреннем защищённом контуре организации. GitHub содержит только код и синтетические/обезличенные данные.

Update:
- batch ETL/ELT по расписанию;
- API/event-driven при изменении записи;
- manual refresh для пилота.

Пересчитываются только изменившиеся записи; используется `profile_version` и журнал изменений.
