# Получение и апдейт цифровых профилей

## Как получить подробный профиль из текстового файла

Исходный TXT/PDF/DOCX/XLSX не превращается сразу в список компетенций. Целевой результат — профиль с исходными фактами, их нормализованными версиями, доказательствами и производными оценками.

**1. Extraction.** Извлечь текст, таблицы и метаданные; определить тип документа.

**2. Entity extraction.** Выделить публикации, авторов, даты, организации, образование, ДПО, дисциплины, проекты, гранты, РИД и другие активности.

**3. Normalization.** Привести даты, названия организаций и типов активности к справочникам; удалить дубли.

**4. Семантическое обогащение.** Определить научную область/тему и ключевые слова.

**5. Сопоставление с КРМ.** Для каждого факта сравнить текст с названием и дескриптором компетенции КРМ. Базовый метод — embedding/NLP + cosine similarity. Сохраняются `similarity` и `confidence`.

**6. Evidence layer.** Для каждого соответствия хранить `source_id`, `raw_text`, `normalized_text`, дату, `competency_id`, `similarity`, `confidence`, `mapping_version`.

**7. Aggregation.** На основании evidence рассчитать уровень компетенции сотрудника.

**8. Validation.** Для критичных связей — экспертная проверка; пользователь может подтвердить/исправить предложенное сопоставление.

**9. Profile JSON.** Собрать подробный цифровой профиль и визуальную карточку.

### Важное уточнение

`profile_example_detailed.json` — демонстрационная структура, вручную сформированная по предоставленному цифровому следу. Она **не является результатом автоматического парсинга исходного TXT**. Это принципиально зафиксировано в поле `source_policy`.

## Нужно ли хранить исходный цифровой след?

Да, но не в публичном GitHub. Raw-слой нужен для воспроизводимости, аудита и повторного расчёта при изменении КРМ. Он хранится во внутреннем защищённом контуре.

Архитектура:
`Raw → Normalized → Competency → Analytics → Presentation`.

## Как делать апдейт JSON-профиля

JSON — актуальная агрегированная витрина, а не единственное хранилище.

1. По расписанию или событию получить новые/изменённые записи.
2. Найти `source_record_id` и проверить дубли.
3. Добавить новые evidence или обновить изменившиеся.
4. Повторно сопоставить только затронутые записи с КРМ.
5. Пересчитать связанные компетенции.
6. Пересчитать агрегированный профиль.
7. Увеличить `profile_version`.
8. Сохранить `mapping_version` и change log.
9. Обновить дату `last_updated`.
10. Сформировать новую версию JSON.

### Триггеры
- плановый ETL/ELT;
- API/event при появлении новой публикации, гранта, ДПО или проекта;
- ручной refresh перед проектной сессией.

### Устаревание
Старые evidence не удаляются: у них есть дата, поэтому в модели используется коэффициент давности `d_is`. Это позволяет сохранять историю и снижать вклад устаревших фактов.

## Минимальный JSON для обновления

`profile_version`, `employee_hash`, `last_updated`, `sources`, `education`, `professional_development`, `teaching`, `research`, `activity_evidence`, `competencies`, `roles`.

Raw-персональные данные остаются во внутреннем контуре; в репозитории используются только синтетические или обезличенные данные.
